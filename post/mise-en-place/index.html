mise-en-place: What I wanted Nix to be

I just realized how lazy my previous blog post was so here’s something that has more detail.

Pre-Nix

Before I discovered Nix, I’ve always had to write out the required system dependencies in the projects’ README, with separate installation instructions for Linux and MacOS. I would then stumble my way into a working setup every time I come back to an old project after a few months.

Nix & the beauty of nix-shell

That changed when I started using Nix to manage project dependencies. Declaring everything in a shell.nix and have Nix build your dev environment in one command was a breath of fresh air.

Leaving Nix

That worked fine when I was mostly working alone, only using Linux and MacOS. I had to ditch Nix again when I started a co-op position where Windows was required (I refused to use WSL).

Even when I moved all of my frontend development to my Mac, I still had to maintain a separate Windows setup for when I had to work outside.

It also started getting annoying when I have to “rebuild” my whole setup when I make a small change. Eventually I found myself moving back to Makefiles and doing checks for presence of tools “manually”. 😭

Discovering mise

When I was setting up my new PC, I wanted to go back to using Arch Linux, mostly because of Omarchy. The “distro” came with a lot of extra packages, most of which I either already had in my previous setup or found useless and tried to get rid of.

However, there was an unfamiliar tool to me that was deeply integrated into the shell which was mise. I felt too lazy to remove it, so I just looked up what it was for, and boy, my mind was blown.

Imagine having a package manager, task runner, and environment variable manager. With one CLI application & one config file, I can replace:

  • Ecosystem/language-specific tools - tools can use multiple backends, so you can also declare tools that you usually have to manually install with npm install -g, cargo install, go install, or dotnet tool install.
    • You can also specify it per-task, so users wouldn’t even have to download the tool unless they run the specific task that needs it
  • pnpm env/nvm - You can simply specify the tool version you want to run for the task/directory, which is perfect for when I have to run multiple versions of node at the same time
  • dotenv - Just define sensitive environment variables in mise.local.toml and ignore from version control
  • Makefile - You can define inputs/outputs so the task only runs if the inputs changed/outputs are missing like in Makefiles
  • npx - Need to run a one-off tool from npm? How about from everywhere else? mise exec <TOOL> -- <TOOL>

Now I can do a fresh clone, run mise dev, and it would install everything and build any prerequisites for me. And even if the tool isn’t available from all of the package backends, I can still fall back to whatever I was doing before, which was one-off, platform-specific scripts. The only difference now is I can add the check as a task dependency, so the only annoying part is writing the script, not running it.

btw did I mention that it’s written in Rust? 🦀
